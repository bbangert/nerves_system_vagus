# Home Assistant Green (RK3566): Vagus product layer

This target is [nerves_system_ha_green](https://github.com/bbangert/nerves_system_ha_green),
the board support for the Home Assistant Green, plus the layer that Vagus
needs on top of it. The board system is vendored under `base/` and holds
everything about the board itself: the boot chain and what is never written,
the disk layout, the A/B slots, `green-install-emmc`, the vendor kernel and
its patches, and the hardware validation record. Start with
[base/README.md](base/README.md). Installing and getting back to stock Home
Assistant OS are in [docs/ha-green-install.md](../docs/ha-green-install.md).

## What this layer adds

| Feature | Description |
| --- | --- |
| Containers | podman 6.1.4 + netavark (nftables) + cgroup v2 |
| Memory tuning | `linux-memory.config` (swap/reclaim, `PANIC_TIMEOUT=10`) and `/etc/sysctl.conf` |
| USB audio | The USB audio class driver, from `linux-bluetooth.config` |
| D-Bus + BlueZ | `dbus-daemon`, `bluetoothd`, `bluetoothctl`, `btmon`, bluez-alsa (SBC). Vagus starts the daemons itself |
| USB Bluetooth | `btusb` (built in, with Realtek, Intel, Broadcom and MediaTek support) and the Realtek, Intel, MediaTek and Qualcomm 6174A dongle firmware from linux-firmware |

The Green has no onboard WiFi or Bluetooth. D-Bus ships because Home
Assistant installs apps by default that need the host system bus (Matter
Server mounts `/run/dbus`), and BlueZ plus the dongle firmware ship so a USB
Bluetooth dongle works. No USB dongle has been tested on the board. There is
no `/etc/bluetooth/main.conf`: the other boards' one tunes an onboard
AIC8800 radio. Broadcom USB dongles whose firmware is a `.hcd` file are not
covered, because linux-firmware does not carry those. Atheros AR3012 dongles
are not covered either: they need the kernel's separate ath3k loader.

`linux-*.config`, `rootfs_overlay/etc/sysctl.conf` and `package/vagus-*`
are synced from the repo's `shared/` by `make sync`.

## How the layers fit

`base/` is a `git subtree --squash` of a tagged nerves_system_ha_green release
(`base/VERSION`). Never edit it here; fix the base repo, tag it, then:

```sh
make base-pull BASE=ha_green REF=v0.1.0   # subtree pull + make sync
```

Three files are generated by `scripts/sync-base.sh` from `base/` plus this
directory's fragments, and carry a DO NOT EDIT header:

| Generated | From |
| --- | --- |
| `nerves_defconfig` | `base/nerves_defconfig` + `nerves_defconfig.fragment` |
| `Config.in` | `base/Config.in` + `Config.in.fragment` |
| `rootfs_overlay/etc/erlinit.config` | `base/rootfs_overlay/etc/erlinit.config` + `erlinit.config.fragment` |

The merge rules are the same as for the other base targets; see
`dragon_q6a/README.md`. `base/` carries its own licensing in
`base/NOTICE` and `base/LICENSES/`.

The build runs the base system's guards (`base/scripts/check-*.sh`, from its
post-build and post-createfs hooks). They hold for this product too, so
nothing in this layer may enable a kernel option the guards forbid (Rockchip
vendor storage, the SFC controller, SPI-NOR support, `/dev/mem`, the MMC test
driver, the FIQ debugger), add an install path for the eMMC, or change the
reserved memory above 4 GiB or the SD card's 3.3 V high-speed mode.

## Container runtime (podman)

The engine, kernel support and runtime mounts are the same as dragon_q6a's
(see `dragon_q6a/README.md`, "Container runtime"), with one difference: the
kernel cmdline needs no cgroup flags. base mounts no cgroup v1 hierarchy,
so `erlinit.config.fragment`'s `cgroup2` mount gets every controller.

Images live under `/root/containers/storage` on the ext4 data partition
(`/dev/rootdisk0p5`).
